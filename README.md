# JANUS

JANUS is a credit-card fraud detection system built on the IBM TabFormer synthetic transaction dataset: an XGBoost scorer over per-user sliding windows enriched with user/merchant history features, plus confidence scoring, three-way routing (approve / step-up / block) and per-transaction SHAP explanations. Around that core it adds adversarial-robustness experiments, drift monitoring, a GraphSAGE model and federated learning, with negative results reported as such (see [Limitations](#limitations)).

## Headline results

All numbers are on a held-out chronological test split (1,827,841 windows, 2,283 fraud), single dataset, single split.

| Metric | Result |
|---|---|
| AUC-PR, baseline (window features only) | **0.7556** |
| AUC-PR, enriched (+ user/merchant/novelty features) | **0.8171** |
| AUC-PR, hardened (adversarially retrained) | **0.9190** |
| False-positive reduction on rare-but-legitimate purchases (baseline → enriched) | **31.7%** (rare purchases) vs **8.8%** (ordinary-purchase control) |
| CPU inference latency (enriched model) | **0.27 ms** mean, single window, 1,000 runs |

Read these with the caveats below before quoting them: the decision thresholds were selected on the test set, there are no confidence intervals, the data is synthetic, and the 0.27 ms figure is model scoring only (no feature assembly, SHAP, Redis or network time).

## Dataset

[IBM TabFormer](https://github.com/IBM/TabFormer) synthetic credit-card transactions: 24.4M transactions, 0.122% fraud. **The dataset is not included in this repository** (the raw CSV is ~2.2 GB). Obtain it by following the data link in the TabFormer repo's README and place the CSV at `Data/card_transaction.v1.csv` (or point `JANUS_RAW_CSV` at it).

JANUS works on a reproducible dev subset carved out by `step1_read_data.py`: 750 sampled users with their full histories, about 9.17M transactions. Train/test is a chronological per-user 80/20 split (7,330,071 train windows, 1,827,841 test windows).

## Architecture

```
 transactions ──► Kafka topic ──► consumer ──► feature assembly ──► XGBoost model
                  (mock bus in       │          (window of last 10 tx    │
                   this repo)        │           + user/merchant/flag    ▼
                                     │           features from Redis)  probability
                                     │                                   │
                                     │                          confidence score (step 10)
                                     │                                   │
                                     │                     three-way routing (step 11)
                                     │                     approve / step_up / block
                                     │                                   │
                                     ▼                          SHAP rationale (step 13)
                              Redis: rolling user                        │
                              state (updated after                       ▼
                              each scored tx)               verdicts topic ──► Streamlit dashboard
```

- **Serving** (`step14_api.py`): FastAPI `/score`, `/health`, `/metrics`, `/history/{user_id}`.
- **State** (`step15_streaming.py`): per-user rolling history in Redis; consumer scores each transaction by calling the FastAPI app in-process and produces a verdict message.
- **What was actually exercised:** Redis was tested against a real local `redis-server`. **Kafka was never run against a real broker**: `kafka-python` adapters exist, but with no broker on `localhost:9092` the code falls back to an in-process mock message bus, which is what all results and the dashboard used.
- **Cold start:** the data contains no fraud in a user's first 68 transactions, so no cold-start model was trainable. Position 0 routes to `step_up`, positions 1-8 to `approve`, everything after to the main model.

## How to run

### Environment

Developed on Python 3.12. `requirements.txt` is pinned to the environment that produced the results.

```bash
python3.12 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
# pyg-lib is not on plain PyPI for this torch build (needed by steps 23-25):
pip install pyg-lib==0.9.0 -f https://data.pyg.org/whl/torch-2.12.0+cpu.html
```

`artifacts/scaler.pkl` and `artifacts/encoders.pkl` are **not committed** (version-sensitive pickles; the originals were made with scikit-learn 1.8.0). They are regenerated by `step2_preprocess_data.py`. The large arrays, parquet files and graphs are also not committed and are regenerated by the pipeline. Budget roughly 15-20 GB of free disk for regenerated artifacts (the training window array alone is ~6 GB, and step 26 writes a ~6-7 GB partition cache).

The committed `artifacts/model_*.json` and `metrics_*.json` are enough to read the results, but **not enough to run the API**: `step14_api.py` also needs the scaler/encoders and the feature parquet files, so run steps 1-8 first.

### Dataset

Place `card_transaction.v1.csv` at `Data/` (or `JANUS_RAW_CSV=/path/to/card_transaction.v1.csv python step1_read_data.py`).

### Execution order

Run from the repo root, in this order. Each script reads artifacts written by earlier ones.

## What each phase does

- **Phase 0 (steps 1-4):** stream the raw CSV into a 750-user subset, clean/encode/scale it with a chronological split, build 10-transaction sliding windows (210 features), train the baseline XGBoost.
- **Phase 1 (steps 5-8b):** add per-user history, merchant/population, and first-occurrence/novelty features (33 extra, 243 total), retrain, and evaluate false positives on rare-but-legitimate purchases.
- **Decision layer (steps 9-13):** cold-start analysis and a position-confound diagnostic; a confidence score; approve/step-up/block routing; probability calibration checks; SHAP rationales.
- **Serving and operations (steps 14-18):** FastAPI scoring service, Redis/Kafka streaming path, Streamlit dashboard, PSI drift monitor, and a PSI-triggered warm-start update guarded by a validation gate.
- **Phase 4, adversarial (steps 19-21b):** CTGAN synthetic fraud; a PPO attacker that perturbs fraud in feature space to evade the enriched model; adversarial retraining; a fresh attacker trained against the hardened model.
- **Phase 5, graph (steps 23-25):** user-merchant-card heterogeneous graph, GraphSAGE classifier, and a fusion experiment with the tabular model.
- **Phase 6, federated (step 26):** Flower simulation across 5 partitions of users with XGBoost bagging.
- **Phase 7 (steps 28-29):** consolidated baseline/enriched/hardened comparison and ablations.

## Limitations

These are material. Please read them before relying on any number above.

- **Synthetic data, one dataset.** Everything is measured on TabFormer with a single chronological 80/20 split. No cross-dataset or real-data test was run, so none of the AUC-PR, calibration, drift or robustness numbers are known to transfer.
- **Fraud-injection artifact.** There is zero fraud in a user's first 68 transactions (earliest fraud at position 68), which looks like an artifact of how fraud was injected into the synthetic data rather than realistic behavior. Because enriched features are history-based, part of the enriched-over-baseline gain could reflect position rather than fraud signal. The position diagnostic (step 9b) judged this "unlikely to be primarily position-driven" but flagged `mcc_user_count` as a strong position proxy. The conservative estimate of the enriched gain is the late-position bucket (15k+ transactions), **+0.026 AUC-PR**, versus the +0.062 headline gain.
- **New-MCC false positives got worse with enrichment.** The 31.7% rare-purchase FP reduction is not uniform: for a first-time merchant category the FP rate rose from 1.38% (baseline) to 2.35% (enriched); hardening brought it down slightly to 2.19%.
- **Adversarial hardening is local, not structural.** The PPO attacker evaded the enriched model 66.5% of the time (harvest mode; 58.8% deterministic). Replaying that same attacker against the hardened model drops evasion to 1.8% (0.5% deterministic), but a **fresh attacker trained directly against the hardened model evades it 64.9%** of the time (48.6% deterministic). The hardening closed the specific known exploit, not the underlying weakness; the code labels this verdict `overfit`. The baseline model was never adversarially tested.
- **GraphSAGE null result.** GraphSAGE reached AUC-PR 0.027 versus 0.817 for the tabular model, and fusing the two (0.9/0.1 weights) slightly reduced AUC-PR (-0.004). No fusion setting was tuned to force a win.
- **Federated learning underperforms centralized.** The federated model scored AUC-PR 0.221 versus 0.817 centralized and helped only 2 of 5 banks relative to training locally. It is a single-machine simulation on one synthetic dataset, so the 5 "banks" are arbitrary user slices, not genuinely non-IID institutions. It also uses XGBoost's parallel-tree mode per client round (a different algorithm than the centralized model), because Flower's bagging aggregator only folds in `num_parallel_tree` trees per update. Step 26 was run in a separate Python 3.13 / xgboost 3.1.2 environment from the rest of the pipeline.
- **Thresholds selected on the test set.** The best-F1 decision thresholds are chosen on the same test data used to report precision/recall/F1, so those figures are optimistically biased. AUC-PR is threshold-free but there is still no separate validation split for model selection.
- **No confidence intervals.** All results are single runs from one seed with point estimates only; differences of a few hundredths of AUC-PR are not statistically qualified. With 2,283 test fraud windows the fraud-side estimates are noisy.
- **Streaming path is partly mocked.** Kafka was only exercised through an in-process mock; there is no real-broker test.
- **Not containerized.** There is no Dockerfile or container setup; the environment is a plain Python venv plus a locally installed Redis.
- **Environment mismatch.** The committed pin set matches the environment behind most results (Python 3.12, xgboost 3.2.0, scikit-learn 1.8.0); step 26 is the exception noted above.
